# fhir-hub Implementation Guide

The published specification: `http://spec.digitalis.nl/fhir`. Conformance artifacts plus the
narrative, built with SUSHI and the HL7 IG Publisher, served as static files.

```bash
npm install                     # once
npm run build                   # pages -> SUSHI -> IG Publisher; output in output/
open output/index.html
```

Then publish. `deploy.sh` runs **on the web server**, against a local document root — it needs
`output/`, `sushi-config.yaml`, `package-list.json` and `hosting/`, but none of the build
toolchain. rsync is not used at either end, because it is not installed on every web server and
was not on this one:

```bash
tar czf - output sushi-config.yaml package-list.json hosting \
  | ssh spec.digitalis.nl 'rm -rf ~/fhir-hub-ig && mkdir -p ~/fhir-hub-ig && tar xzf - -C ~/fhir-hub-ig'

ssh spec.digitalis.nl 'cd ~/fhir-hub-ig && hosting/deploy.sh /srv/spec.digitalis.nl'
hosting/verify.sh https://spec.digitalis.nl
```

About 18 MB over the wire. The `rm -rf` is not politeness: without it a file a later build stopped
producing would linger in the staging tree and be published again.

`npm run build` checks its prerequisites before it starts and names the fix for whichever is
missing, so run it first and let it tell you. There are four: Java, Node, **Jekyll**
(`gem install --user-install jekyll` — the IG Publisher shells out to it), and the publisher jar:

```bash
curl -sL -o .pkg/publisher.jar \
  https://github.com/HL7/fhir-ig-publisher/releases/latest/download/publisher.jar
curl -sL -o .pkg/validator_cli.jar \
  https://github.com/hapifhir/org.hl7.fhir.core/releases/latest/download/validator_cli.jar
```

Neither jar is committed (~240 MB and ~190 MB). The build reaches the network for its FHIR
packages and for `tx.fhir.org`, and fails on a QA error while a QA warning is expected — see
*Expect warnings* below.

## What is source and what is output

| | |
| --- | --- |
| `input/fsh/` | **source.** The profiles, extensions, terminology and examples |
| `../IMPLEMENTATION_GUIDE.md` | **source.** The entire contract narrative |
| `pages/` | **source.** The four pages that are about the publication rather than the interface: the front door, the change policy, the changelog, the download instructions |
| `sushi-config.yaml`, `ig.ini` | **source.** Identity, page list, menu, template |
| `hosting/` | **source.** The nginx configuration and the deploy script |
| `input/pagecontent/` | generated by `scripts/build-pages.mjs`. Not committed |
| `fsh-generated/` | generated by SUSHI. **Committed** — see below |
| `output/`, `temp/`, `template/` | generated by the publisher. Not committed |

**The narrative is not written here.** It is written in `../IMPLEMENTATION_GUIDE.md` and split
into pages by `scripts/build-pages.mjs`, because a specification that exists twice is a
specification that disagrees with itself. Editing a file under `input/pagecontent/` loses the edit
on the next build.

The script fails rather than guesses, and three lists have to agree: the guide's `##` sections,
the `SECTIONS` table in the script, and the `pages:` block of `sushi-config.yaml`. Add a section
to the guide and the build stops until it has been given a page — which is the point. It also
rewrites the guide's intra-document anchors into cross-page links, so `](#profiles)` keeps working
in both places.

## Things worth knowing

**The ids are load-bearing.** SUSHI derives a canonical as
`{canonical}/StructureDefinition/{Id}`, and those canonicals are on the wire — see
`fhir/DigitalisExtensions.java`, `fhir/Systems.java` and `fhir/Profiles.java`. Renaming an id, or
editing `canonical:` in `sushi-config.yaml`, is a silent breaking change for every payload in the
field. `IgCanonicalsTest` in the Maven build fails if the two drift apart.

**Do not define the G-Standaard code systems here.** The tables are licensed and cannot be
distributed, so a definition would have to be `content: not-present` — and a value set that
includes such a system cannot be expanded, which turns every coding in it into a validation
error. Left undefined, the system is unknown to the validator and its codings become warnings,
which is the only way the `required` bindings in `terminology.fsh` can be satisfied.
`TerminologyEnforcementTest` in the Maven build fails if one is added.

**These profiles ARE enforced at runtime**, so editing one changes what the service accepts.
`fsh-generated/resources` is committed and copied into the jar by the Maven build — the Docker
image builds with Maven and no node, so it cannot regenerate them. After editing any FSH, run
`npm run sushi` and commit the result, or the running service keeps enforcing the old profile.
Only `StructureDefinition-*`, `ValueSet-*` and `CodeSystem-*` are copied; the
`ImplementationGuide-*` resource SUSHI now also emits is documentation, and stays out of the jar.

**The parent is plain R4, not nl-core**, for reasons that were checked rather than assumed. See
*Profiles* in `../README.md`.

**`deploy.sh` needs no root and no rsync, and it publishes by rename.** The release is assembled
in `.fhir-publishing.$$` beside the document root and swapped in with two renames, so the live tree
is never a half-copied mix of two releases and files a later build stopped producing cannot
accumulate. Previously published snapshots are moved across into the staging tree, which is why
they survive the swap.

Four things about running it unprivileged are easy to get wrong, and all four are handled and
tested:

- a personal `umask` of 077 would publish a tree the user nginx runs as cannot read — a 403 on
  every page, from a deploy that reported success. The script sets `umask 022` and sweeps `a+rX`
- `rsync` is not installed on every web server and is not on this one, so `cp`, `mv` and `chmod`
  do all the work
- `cp -a` and `rsync -a` both try to preserve ownership, which only root can do. `cp -R`
- **renaming a directory needs the write bit on the directory itself**, because its own `..` entry
  is rewritten — so a snapshot deliberately left read-only cannot be moved until `u+w` is restored,
  and re-locked afterwards. This one only showed up when a second release was carried over

Installing the nginx includes and reloading is the only part that wants privilege, and the script
deliberately does not attempt it.

**Jekyll has to be on PATH, and `npm run build` is what puts it there.** The IG Publisher execs
`jekyll` by bare name and has no option to be told where it lives, so a `gem install --user-install`
— which is the normal way to install it and puts the binary somewhere no default PATH includes —
produces a Java stack trace 45 seconds into an otherwise healthy build:

```
Cannot run program "jekyll" (in directory ".../ig/temp/pages"): error=2
```

Nothing in that mentions gems or PATH. `scripts/build.sh` assembles the PATH from `gem env gempath`
rather than hard-coding a directory with a ruby minor version in it, and checks for jekyll before
doing any work. That is the reason the build is a script rather than a chain of npm scripts, and
the reason to run `npm run build` rather than the publisher directly.

**`ig.ini` takes no comments.** The publisher's ini reader treats a `;` line as content and then
reports that it cannot find an `ig.ini` at all, which is a long way from the cause. Keep that file
to its three lines.

**Expect warnings, and read them.** A clean run is `0 errors`, not `0 warnings`: the G-Standaard
codes cannot be validated, the payloads carry no narrative, and the `data-absent-reason`
references have no display. `input/ignoreWarnings.txt` suppresses only the four template-fragment
warnings, and says why — muting the payload warnings would also mute the first sign of a real
problem. `output/qa.html` is the report; `hosting/deploy.sh` refuses to publish a build whose QA
reports errors.

**The narrative language is Dutch, inferred from `jurisdiction: NL`.** That is why the QA report
and the generated resource narratives are in Dutch while the prose is in English, and why a LOINC
`display` must be LOINC's *Dutch* term: a validator with LOINC loaded checks the display against
the narrative language and rejects anything else. The examples send no LOINC display for that
reason.

## Validating by hand

`IgExampleConformanceTest` in the Maven build validates every example against the profile it
claims, so this is the way to see the detail rather than the way to find out:

```bash
npm run validate-examples
```

All four examples must report `0 errors`.

## Cutting a release

The release number lives in four places and they have to agree. Nothing derives one from another,
because a release is a decision rather than a build artifact — but `deploy.sh` refuses a release
missing from `package-list.json`, and `IgCanonicalsTest` refuses profiles that lost the stamp.

1. `sushi-config.yaml` — `version:`, and `status:`/`releaseLabel:` if the maturity changed
2. `package-list.json` — a new entry: version, **date**, desc, path, status, `current: true`, and
   `current` removed from the entry it replaces
3. `pages/changelog.md` — an entry with the same date, grouping changes by whether they can affect
   a payload an integrator already sends. See `pages/versioning.md` for what each level promises
4. `npm run build`, then commit `fsh-generated/` — the profiles carry the new version and the jar
   ships them

Then push and publish as under *Hosting* below, and run `hosting/verify.sh`. The date in step 2 and
step 3 is the day it goes out: if publication slips, move both.

## Hosting

`hosting/deploy.sh` copies the files. The server half is two nginx includes —
`hosting/nginx-maps.conf` in the `http` context and `hosting/nginx-fhir.conf` inside the
`spec.digitalis.nl` server block, split so neither has to be merged into a vhost that already
owns its certificate and its `/`. `hosting/apache-htaccess` is the same rules for Apache, and is
the one that has actually been tested end to end. Between them they make the
canonicals dereference, which is the part the publisher does not do:

- `/fhir/StructureDefinition/fhirhub-Patient` — the canonical, mapped onto the publisher's flat
  `StructureDefinition-fhirhub-Patient.{html,json,xml,ttl}`. `Accept` picks the representation,
  `?_format=` overrides it, `Vary: Accept` keeps a cache from mixing them
- `/fhir/<version>/…` — a frozen copy of each release, so an integrator can pin one. `deploy.sh`
  refuses to overwrite a published snapshot
- both schemes, with `https` **required**: the canonical in every payload is an `http` URL and
  stays one, but the HL7 validator refuses to *fetch* over plain http (SSRF protection, on by
  default), so an http-only deployment is readable in a browser and unusable by tooling

Read the header comments in both files before changing either.
